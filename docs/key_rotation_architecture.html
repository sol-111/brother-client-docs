APIキー 自動ローテーション 構成図

Webhookでキー更新を検知し、Bubble側の保管キーを自動で差し替える構成（DB方式）
なぜ構成変更が必要か
  • 現在のキーは API Connector のエディタ設定（Private key in header）として保存されており、実行時に外部から書き換える公開APIが存在しないため、自動ローテーション不可。
  • Bubbleには「APIで更新できるネイティブのシークレット保管庫」がない（2025年追加の Secrets Scanner は漏洩検知機能であり保管庫ではない）。
  • → キーをエディタ設定からデータベースのレコードに移し、API Connector 側は動的パラメータで受け取る構成に変更する。

構成要素

フロー1：ローテーション（キー更新時）3ステップ

ステップ → 1. キーをローテーション発生時のみ 2. Webhook POSTAWS → Bubble 3. 検証 → キー上書きBubble内で完結
どこで？ ☁️ AWS ☁️ AWS → 🫧 Bubble 🫧 Bubble（サーバー側）
何が起きる？
ブラザーが新キーを発行
Usage Plan に新旧キーを併登録。旧キーは有効なまま維持する。
Lambda / EventBridge が発火
新キー＋共有シークレット（または署名）を Backend Workflow のエンドポイントへPOST。
Backend WF が検証して上書き
シークレット／署名を照合し、正規の通知なら ApiCredential レコードを新キーで上書き。結果をレスポンスで返す。
次に
どうなる？
→ 2. Webhook POST が自動発火
→ 3. 検証 → キー上書き
検証NGなら拒否（キーは変更されない）
終端
AWS側がレスポンスで成功を確認してから旧キーを無効化。以降の呼び出しは自動的に新キーになる。
※ 画面が狭い場合は表を横にスクロールできます

フロー2：通常のAPI呼び出し2ステップ

ステップ → 1. 最新キーを取得毎回の呼び出しで実行 2. x-api-key を付けて呼び出しBubble → AWS
どこで？ 🫧 Bubble（Backend WF） 🫧 Bubble → ☁️ AWS
何が起きる？
ApiCredential からキーを読込
Privacy全閉じのため、ignore privacy rules を有効にした Backend WF でのみ読める。
API Connector を実行
動的パラメータにキーを差し込み、API Gateway を呼び出す。
次に
どうなる？
→ 2. API呼び出し へ
終端
常にDBの最新キーで認証されるため、ローテーション後も改修なしで通り続ける。
※ 画面が狭い場合は表を横にスクロールできます

セキュリティ要件

🔒 Privacy Rules を全閉じ（必須）
ApiCredential は "Everyone else" の検索・表示チェックをすべてOFF。値がクライアントに送信されなくなるため、開発者モード（debug_mode）・コンソール・Data APIのいずれからも見えない。あわせてこのDataTypeのData APIも無効化しておく。
🖥️ サーバー側でのみ使用（必須）
キーの読み取りとAPI呼び出しは Backend workflow（ignore privacy rules）だけで行う。API Connectorの動的パラメータはprivate指定不可のため、クライアント側WFから呼ぶと値がブラウザの通信に載る。
✍️ Webhook受け口の認証（必須・方式選定）
新キーが流れるため受け口の認証は必須。①共有シークレットヘッダーをWF条件で照合（最低限・実装容易）、②HMAC署名検証（推奨・要cryptoプラグイン）。
※BubbleのワークスペースAPIトークンは全権限を持つため、ブラザーへの共有は不可。
♻️ 新旧キー併用期間（推奨）
API Gateway の Usage Plan に新旧キーを併登録し、Bubble側の更新完了を確認してから旧キーを無効化。切替時のダウンタイムをゼロにする。更新成否をWebhookレスポンスで返すとAWS側から確認可能。

現状方式との比較

観点現状（Connectorにキー直書き）本構成（DBレコード方式）
自動ローテーション ✕ 不可（エディタ設定のため外部から更新不能） ◯ 可能（Webhook → レコード更新で完結）
クライアントからの可視性 見えない（private key はサーバー側で代入） 見えない（Privacy全閉じ＋Backend WF限定が前提）
エクスポート（.bubble）への漏洩 ✕ settings.secure に平文で含まれる（検証済み） ◯ ランタイムデータのため含まれない
実装コスト —（現状のまま） API Connector改修＋Backend WF追加＋AWS側Webhook実装
※ DB方式に移行すると、エクスポートファイルにAPIキーが平文で残る問題（本アプリで検出済み）も同時に解消される。

代替案：AWSプロキシ方式

🧩 Bubbleにキーを一切持たせない構成
AWS側にプロキシ（Lambda等）を置き、Secrets Manager からキーを都度取得して API Gateway を呼ぶ。Bubble→プロキシ間は別の固定認証（例：Bubble専用の長期キー）で接続。ローテーションが完全にAWS内で完結し、Bubble側の改修・Webhook受け口・キー保管がすべて不要になる。ブラザーがAWSを管理している前提なら、運用上もっともシンプルで安全。
